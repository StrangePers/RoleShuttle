---
name: roleshuttle
description: Use when the user chooses RoleShuttle to divide a coding task among workers, select models by role, or obtain independent review. Return findings and questions to the main chat.
---

Use this workflow when the user chooses delegation. Keep the user's conversation model and native permissions. The main agent owns the requirements, decomposition, review and final answer.

If the user selects a cloud preset, run `roleshuttle preset` to list names, then `roleshuttle preset NAME` for its routing settings. Use `--role ROLE` for a single assignment or `--lane LANE` for an explicitly selected Go task category. Apply the model and any effort setting through an authorized executor that supports both. Check the returned model identity. For OpenRouter Free, check the current provider catalog for tools and free pricing before choosing a listed preference. If the intended route cannot be verified, return the choice to the main chat. Looking up a preset does not start a worker or change the conversation model.

For a Codex text stage use `roleshuttle codex-stage --role implementer --input -` with the user's approved excerpts on stdin. Select a different model or reasoning effort only as authorized. Read the JSON receipt. On `needs_input`, ask the returned question in the main chat and include the answer in a new stage if needed. For independent review send the original requirements and the actual proposal to a fresh `--role reviewer` call. On failure report the stage as incomplete. Apply reviewed changes through the main agent and run project checks before accepting. Use the task runtime below when a worker needs worktree access.

The user may choose a lightweight conversation model. Keep routine edits in the chat when another call would add overhead. For a bounded lookup or implementation proposal, run `roleshuttle delegate --profile <profile.json> --role research --input -` (or select `implement`). Use the operator's profile and send only the task and approved excerpts.

When a consequential decision needs specialist judgment and a second opinion, run `roleshuttle consult --profile <profile.json> --input -`. Include the decision, constraints, relevant source and acceptance criteria. The command calls the configured specialist, sends the task and proposal to the configured reviewer in a fresh context, and returns both receipts to you. You choose when to invoke it. Inspect the status and check advice against the actual files and tests. A completed review can disagree with the specialist. If the two disagree, resolve it with evidence or ask the user in the original chat. Relay only the relevant human answer. Never silently substitute a different model or retry an incomplete stage at extra cost.

Local text workers receive no tools or filesystem access. Apply scoped changes through the native client's permitted tools and run the project's checks yourself. For durable tasks and worktree-writing workers, use the guarded runtime procedure below.

For the local-task workflow, use `roleshuttle local-project discover <checkout>` to inspect the project. On `PROFILE_MISSING` or `RESOLVED` with `resolution: inherited`, save the original local-task contract without `project_id` and run `roleshuttle local-task prepare <contract.json> --checkout <checkout> --request-id <stable-id>`. Tell the user to review and confirm the profile in the local browser form. Keep the command running while they decide. A prepared task resumes the usual worktree and routing workflow. On `CANCELLED` or `EXPIRED`, stop and report the result. Keep Extra Usage off.

1. Identify which stages can finish independently. For each stage specify the goal, allowed files, data boundary, role and acceptance checks. For a small task, direct work may be cheaper. Use the configured runtime's trusted project schema and allowed routes. Never infer permission to send code or incur extra charges from a model name.
2. Start a bounded stage with `roleshuttle task run --contract <local-contract.json> --wait-seconds 0`. Record the returned task ID. Keep contracts and actual reports outside the public source tree. An unavailable runtime or route is a blocker for that stage.
3. Collect a compact result with `roleshuttle task wait --task-id <id> --collect --wait-seconds 30`. Read the diff and referenced evidence when needed. Avoid putting raw logs or the whole conversation in every worker prompt. Workers return to the controller without recursive delegation.
4. If a human decision is pending, ask in the original conversation. Send the answer using `roleshuttle task answer-decision --task-id <id> --revision <revision> --request-id <request> --answer <answer>`. Do not put sensitive text in command-line arguments. Reading or recording a decision does not start another job.
5. Have an independent reviewer inspect risky changes. Review the actual worktree before running trusted checks with the runtime's pinned fingerprint. A correction invalidates earlier evidence. Respect the configured project acceptance mode. Accepting and merging are separate operator decisions.
6. Report the outcome, actual roles/models, checks, retries and any unknown usage. Separate premium usage, total usage, elapsed time and actual charges. If a decision is valuable beyond this task, propose a short Project Fieldnotes entry with a shareable source and a revisit condition. Write it only to the project notebook the operator selected.
